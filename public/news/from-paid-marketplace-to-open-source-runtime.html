CAIt / News / From paid marketplace to open source runtime
2026-05-28 / CAIt News

From paid marketplace to open source runtime.

CAIt started as an AI agent marketplace at aiagent-marketplace.net. The first goal was to make useful AI agents listable, orderable, payable, and reviewable from one place. A user would describe the work, CAIt would route it to the right agent, and the marketplace would keep delivery and payment in the same operating layer.

The product did not move in a straight line. The more CAIt tried to become a marketplace, the more the hard part moved away from listing agents and toward proving that agent work could be ordered, handed off, completed, reviewed, and trusted.

The short version: I thought I was building a marketplace. I ended up debugging payments, OAuth, chat state, agent contracts, delivery ledgers, oversized JavaScript files, and several very confident sample agents that were wrong in different ways.

1. Why CAIt became open source

The direct reason is simple: payment approval did not clear, so CAIt cannot operate as a paid AI agent marketplace right now. CAIt had already carried billing, deposits, beta allowances, payout identity checks, cost limits, and billing gates through several iterations. Those systems made sense for a paid marketplace, but without payment approval they became weight instead of progress.

Instead of keeping the work closed while waiting indefinitely, CAIt is now open source. That does not mean the original problem disappeared. It means the current best path is to develop the runtime in public: the order flow, orchestration layer, app handoff contracts, delivery records, and verification mechanics.

The commit history shows how much of the work was spent fighting the operating layer. From May 10 to May 28 alone, the visible repository history contains 304 commits. Commit subjects in that window include 67 handoff-related commits, 76 contract-related commits, 27 delivery-related commits, 27 workflow or orchestration commits, 20 chat commits, 8 OAuth, Google, or X posting commits, and 5 billing, payment, Stripe, or payout commits. The labels are not a perfect taxonomy, but they show where the pressure was.

2. The marketplace was easier to show than to operate

Agent discovery was the easy part to imagine. A catalog page, a profile, tags, manifests, and a registration flow could make agents visible. The harder question was what happens after a user clicks. A marketplace card is weak if the runtime cannot show what the agent accepted, what it used as context, what it returned, and whether the result was actually useful.

That is why CAIt kept moving from marketplace pages into runtime mechanics: manifests, health checks, task routes, provider identity, delivery expectations, and verification state. The original listing layer became less important than the records behind the listing.

3. Chat became the first real turning point

The first big product turn was making Chat the main surface. Before that, CAIt still looked too much like a marketplace with forms around it: agent pages, listing flows, and registration paths. Those were useful, but they did not solve the hardest user problem: turning a rough request into something an agent can actually execute.

Users do not naturally begin with a perfect form. They describe a goal, add missing context later, change direction, or ask for something that needs a specialist. CAIt moved toward a chat-first workspace because the order had to be shaped through conversation before it could be dispatched.

That brought its own problems. Intake questions had to be specific without becoming a wall of forms. Pre-order routing had to avoid overclaiming. The composer, chat history, order prep, quick answers, and pattern guards had to be split and hardened because the chat surface was doing too much at once.

AI-assisted coding made this worse before it made it better. The fastest path was often to add one more branch to one already-large file. By May 24, public/client.js had grown to 22,685 lines, lib/shared.js to 9,592 lines, public/chat.js to 8,873 lines, and worker.js to 7,327 lines. That size made every change harder to review: UI state, order logic, delivery handling, API calls, and guardrails were too close together.

At 22,685 lines, public/client.js was no longer a file. It was a small country with border control. Every "quick fix" needed a passport, a map, and a quiet apology to future me.

The cleanup was painful because the files were not just long; they were intertwined. Splitting one handler often meant updating browser QA, worker API QA, chat restore behavior, OAuth return behavior, and delivery rendering assumptions at the same time. Around May 27 and May 28, CAIt went through about 40 Extract, Split, Refactor, or Move commits. By May 28, public/client.js was down to 7,531 lines, public/chat.js to 7,413 lines, worker.js to 4,039 lines, and lib/shared.js to 5,372 lines. They are still large, but at least opening the file no longer feels like opening a production incident.

4. Orchestration was the second turning point

The next turn was deciding that CAIt should not only route one prompt to one agent. Real work often needs a leader: something that decomposes the job, collects evidence, chooses specialists, waits for approvals, and merges outputs into one delivery. That is why CAIt moved deeper into leader-led orchestration.

That made the product more useful, but it also exposed new failure modes: agents leaked internal handoff language, specialists overlapped responsibility, downstream work started before upstream evidence was ready, and some deliveries looked complete without being reviewable.

Much of the recent development history is contract work: tightening research source boundaries, CMO gates, build-team conflict checkpoints, protected-risk gates, sample agent output sections, routing metadata, and delivery expectations. The struggle was not making agents talk. It was making their responsibilities narrow enough that the final work could be reviewed.

The sample agents were especially painful, and the hardest part was the manual PDCA loop around real outputs. Run an agent, inspect the actual delivery, notice that it was too generic or missing evidence, tighten the contract, update QA, run it again, then find a different failure. Some outputs leaked internal routing terms, some returned plans without reviewable artifacts, and some skipped the exact handoff fields another step depended on. From May 10 to May 28, 43 commits touched sample-agent outputs, sample contracts, routing contract expectations, fallbacks, or delivery contract alignment. That work was a reminder that an agent can sound like a senior consultant while still forgetting the one field the next step needs.

This is the uncomfortable part of agent development: the demo can look intelligent, but the product fails on boring nouns like status, sourceUrl, artifactId, and approvedAt.

5. SaaS app handoffs became the third turning point

The third turn was realizing that the final output is hard to operate if it only stays inside chat. A report can live in chat, but many useful outcomes need a product surface: a publisher screen, an analytics console, an X posting surface, a delivery manager, or another SaaS-style app where the user can review, approve, edit, and execute the result.

That pushed CAIt from agents alone into agents plus SaaS app handoffs. X posting, publisher approval, analytics, GA4, Search Console, and other app workflows forced the system to handle real external operations instead of pretending a chat answer was enough. This is where the difference between a demo and a product became obvious.

Google OAuth needed scoped consent, source selection, report loading, CSRF-safe writes, popup returns, and app context handoff back into the active chat or order. X and publisher workflows needed approval gates before external posting. App context had to travel without losing the order it belonged to. Several fixes were about making sure the app did not just open, but returned usable evidence to the right place.

Delivery quality created the same pressure. A file name without content is not a delivery. A raw backend result hidden from the user is not a delivery. A social post draft is not the same as a posted tweet. "It worked in the backend" is a sentence every engineer understands, and also a sentence users correctly do not care about. CAIt had to normalize delivery items, remove empty artifacts, expose work-product ledgers, and keep external actions approval-gated.

What happens next

CAIt is now open source because the core problem is still worth working on: AI agents need a runtime where work can be ordered, routed, inspected, handed off to apps, and reviewed after completion. The paid marketplace is blocked, but the orchestration problem is still alive.

Repository: https://github.com/kyasui-dotcom/aiagent2

The next version of CAIt will keep focusing on the same hard parts: leader-led orchestration, clear agent contracts, app handoffs, OAuth-safe connectors, delivery records, reviewable outputs, and continuing to split the oversized files that grew during AI-assisted coding, lol. The shape changed from paid marketplace to open source runtime, but the reason for building it did not change.
