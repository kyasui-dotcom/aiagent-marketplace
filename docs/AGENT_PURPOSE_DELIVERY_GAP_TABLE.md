# Agent Purpose / Delivery Gap Table

This review treats every built-in agent as an external-style provider endpoint. Do not use this table to create a shared action registry, shared action enum, or worker/client branch table. Each improvement should be copied into the relevant agent file only, owned by that agent's own definition, manifest, provider result, and delivery validation.

## Review Rules

- Each agent owns its own purpose, action boundaries, authority policy, and delivery contract.
- Worker, client, orchestration, and shared modules may store or display agent-provided data, but must not interpret agent-specific action ids.
- A strong agent is not just a prompt. It should define what it prepares, what it hands off, what it must not claim, and what a valid delivery contains.
- Gaps below are delivery-quality risks, not permission to centralize behavior.

## Highest-Impact First Pass

1. `x-post.js`, `email-ops.js`, `cold-email.js`, `instagram.js`, `reddit.js`, `indie-hackers.js`: external communication boundaries are user-visible and risky.
2. `ads-planner.js`, `campaign-operations.js`, `cmo-leader.js`: money, campaign state, Publisher handoff, and channel ownership need sharp separation.
3. `seo-specialist.js`, `writer.js`, `landing.js`: these generate the most visible deliverables and need mode-specific contracts.
4. `code.js`, `build-team-leader.js`, `cto-leader.js`: implementation work needs file/test/rollback contracts.
5. Research and operations agents: add source/status/accountability tables so outputs do not look stronger than the evidence.
